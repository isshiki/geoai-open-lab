# 分析前の判断と実行の記録

新しい分析では、Notebookを作り込む前に入力が問いに答えられるかを確認する。結果の良し悪しと、実行が成功したかは別に記録する。既存分析への遡及適用や一括改訂は行わない。

分析を担当するエージェントが既存資料から記入し、実行中も更新する。ユーザーへ毎回ひな形の記入を求めない。判断に必要な情報が不足する場合や目的の変更が必要な場合に、その点を具体的に報告する。書式を埋めることより、入力不足で早く止まることと結論の根拠を残すことを優先する。

## 既存の仕組みとの役割分担

| 既存の記録 | この手順で補うもの |
| --- | --- |
| [データポリシー](data-policy.md)、ソース別の利用条件 | 必要な空間・時間・分類の細かさに入力が適合するかという判断 |
| 各実験のmanifest、入力ハッシュ、環境・再現コマンド | 実行前の仮定、比較対象、判定方法と変更理由 |
| テスト、Notebook全セル実行、再実行一致 | 失敗・中止・不採用も含む実行の一覧 |
| 検証記録、記事引き継ぎ | 当初の問いに答えられた範囲と、探索で追加した内容 |

版・チェックサム・コマンドを二重管理しない。正本のmanifestやソース文書を参照し、変更時には別版を残す。

## 最小の使い方

1. [適用判断・計画テンプレート](templates/analysis-plan.md)を各テーマの `docs/<analysis>-plan.md` に置く。小さな集計なら各項目1文でよい。対象外は理由、未確認は解消方法を書く。
2. 必要入力・権利・検証可能性を確認する。**使用不可なら分析実装を停止する。未確認を使用可能扱いしない。** 条件付きなら、実行前に満たす条件と解消証拠を記録する。入力の調査だけは続けられる。限定した問いなら使える場合は、問いを縮小した別版として判断し直す。
3. 実行前に計画の版・日付・内容を固定する。既に結果を見たものを確認的分析と呼ばない。機械学習や選択肢の多い比較では、分割の漏洩、空間重複、seed、全候補、採否基準まで具体化する。
4. [実行台帳](templates/analysis-runs.md)へ開始を追記してから実行し、終了・失敗・中止を追記する。既存の実行コードやmanifest生成を作り直す必要はない。
5. テスト・Notebook・再実行・図の確認は従来どおり行う。[引き継ぎ追加項目](templates/analysis-handoff.md)を記事資料へ転記する。失敗した実験も、何が不足したかを安全な文書に残せる。

計画は結果に合わせて上書きしない。変更時は版を増やし、旧版またはGitコミット、変更日、変更理由、すでに見た結果の範囲を残す。予定外の分析は探索的として分離する。悪い結果を消したり、良い結果だけを主結果に昇格させたりしない。

## 保存場所と公開

- 公開する計画・検証要約はテーマ内 `docs/`。安全性確認済みの情報だけを置く。
- 詳細な台帳はテーマ内 `data/cache/<analysis>/runs.md`、実行ごとの成果物はその下の異なる実行IDディレクトリへ保存する。計画の固定コピー・ハッシュ、未コミット差分、lockfileのハッシュも必要に応じて同じ領域へ保存する。
- 手動追記を基本とする。台帳は改ざん防止システムではない。過去行の修正・削除をせず、訂正イベントで元のイベントIDを参照する。異常終了で終了記録がない実行は成功扱いせず、復旧後に中断の確認を追記する。
- 実行IDは再利用しない。再試行にも新IDを割り当てる。並行実行時は実行IDごとに台帳を分け、同じファイルを同時編集しない。
- トークン、署名付きURL、生データ、個人環境の絶対パスを台帳・公開要約へ貼らない。例外の全文や環境変数の一括保存も避ける。認証なし公式URLとテーマ相対パスを使う。
- 台帳や失敗記録を保持することは、機密を保存する許可ではない。混入時は公開を停止し、削除理由と影響を秘密値なしで記録する。データ保管・公開条件はデータポリシーを優先する。

## 導入例と次の候補

[GeoJSON実験の事後点検例](../projects/poi/docs/geojson-analysis-review.md)は、既存結果を変えずに適用した例。事前登録の証拠としては扱わない。

POI名寄せを将来行う場合は、対応ラベルの品質、空間・チェーン単位の漏洩、誤結合と見逃しの評価可能性を着手前に確認する。ルール・Embedding・LLMの比較実装はこの導入には含めない。
